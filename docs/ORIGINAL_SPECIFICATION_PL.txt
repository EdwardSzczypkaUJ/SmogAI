Jesteś seniorem Python, architektem systemów danych, inżynierem MLOps oraz specjalistą Machine Learning. Masz zaprojektować i zaimplementować pierwszą produkcyjnie sensowną wersję systemu prognozowania jakości powietrza w Polsce.

Nie ograniczaj się do opisu architektury ani pseudokodu. Przygotuj kompletny, uruchamialny projekt wraz z kodem, konfiguracją, testami, skryptami instalacyjnymi i instrukcją wdrożenia.

Aktualna data to 2026 rok. Przed implementacją zweryfikuj w oficjalnej dokumentacji aktualnie działające API GIOŚ i IMGW. Nie opieraj się na historycznych, potencjalnie wyłączonych endpointach.

# 1. Cel systemu

System ma:

1. cyklicznie pobierać rzeczywiste dane jakości powietrza z GIOŚ,
2. pobierać rzeczywiste dane meteorologiczne z IMGW,
3. przechowywać pełną historię lokalnie,
4. kontrolować jakość danych,
5. dopasowywać stacje GIOŚ do najbliższych stacji IMGW,
6. przygotowywać dane do uczenia maszynowego,
7. trenować modele lokalnie,
8. generować prognozy PM10 i PM2.5,
9. zapisywać prognozy przed poznaniem rzeczywistego wyniku,
10. później porównywać prognozy z rzeczywistymi pomiarami,
11. obliczać błędy modeli,
12. przygotowywać lekkie dane potrzebne do wizualizacji,
13. przesyłać te dane na zewnętrzny serwer,
14. prezentować wyniki w internetowym dashboardzie.

Całe pobieranie danych, przetwarzanie, trenowanie modeli oraz prognozowanie ma odbywać się na komputerze lokalnym.

Serwer ma służyć wyłącznie do:

* odbierania gotowych wyników,
* przechowywania danych potrzebnych do wizualizacji,
* udostępniania dashboardu,
* prezentowania map, wykresów, prognoz i błędów.

# 2. Podział systemu

Projekt podziel na dwa niezależne komponenty.

## 2.1. Komponent lokalny

Komponent lokalny odpowiada za:

* pobieranie danych GIOŚ,
* pobieranie danych IMGW,
* lokalną bazę danych,
* walidację i kontrolę jakości,
* przygotowanie cech,
* trenowanie modeli,
* wykonywanie prognoz,
* weryfikację wcześniejszych prognoz,
* przygotowanie snapshotów dla dashboardu,
* publikowanie danych na serwer,
* obsługę kolejki niewysłanych publikacji,
* wykonywanie zadań przez `cron`.

Komponent lokalny ma działać na Linuxie.

Preferowane środowisko:

* Ubuntu lub Debian,
* Python 3.12,
* lokalne środowisko `.venv`,
* SQLite,
* `cron`,
* skrypty Bash,
* opcjonalnie `flock`,
* bez Dockera, Airflow, Kafki, Celery i Kubernetes w pierwszej iteracji.

## 2.2. Komponent serwerowy

Komponent serwerowy odpowiada za:

* odbieranie publikacji przez HTTPS,
* uwierzytelnianie tokenem API,
* walidację przesłanych danych,
* idempotentne zapisywanie publikacji,
* ochronę przed duplikatami,
* udostępnianie danych dashboardowi,
* prezentację wyników.

Serwer nie może:

* pobierać danych GIOŚ ani IMGW,
* trenować modeli,
* przygotowywać cech,
* wykonywać ciężkich obliczeń,
* przechowywać pełnych surowych danych, jeśli nie są potrzebne do wizualizacji.

# 3. Harmonogram lokalny za pomocą cron

System lokalny ma być uruchamiany przez standardowy `cron`.

Nie używaj w pierwszej iteracji:

* Airflow,
* Prefect,
* Celery,
* rozbudowanych systemów orkiestracji,
* usług chmurowych wymagających dodatkowej infrastruktury.

Przygotuj przykładowy `crontab`, który realizuje następujący harmonogram:

## Co godzinę

* pobranie danych GIOŚ,
* pobranie danych IMGW,
* kontrola jakości,
* zapis nowych pomiarów,
* weryfikacja wcześniejszych prognoz,
* wykonanie nowych prognoz,
* przygotowanie snapshotu,
* publikacja snapshotu na serwer.

Przykładowo:

```cron
7 * * * * /opt/smog-ai/scripts/run_hourly.sh
```

Nie uruchamiaj zadania dokładnie o pełnej godzinie, aby uniknąć sytuacji, w której API nie opublikowało jeszcze pełnego pomiaru.

## Raz dziennie

* rozbudowany raport jakości danych,
* uzupełnienie braków,
* ponowna próba pobrania brakujących pomiarów,
* czyszczenie starych plików tymczasowych,
* ponowne wysłanie niewysłanych publikacji.

Przykładowo:

```cron
35 2 * * * /opt/smog-ai/scripts/run_daily.sh
```

## Raz w tygodniu

* ponowne przygotowanie zbioru uczącego,
* trenowanie modeli,
* walidacja modeli,
* porównanie wyników,
* zapis nowej wersji modelu,
* aktywacja nowego modelu tylko wtedy, gdy spełnia określone kryteria jakości.

Przykładowo:

```cron
20 3 * * 0 /opt/smog-ai/scripts/run_weekly_training.sh
```

## Raz w miesiącu

* pełny raport jakości,
* archiwizacja,
* sprawdzenie rozmiaru bazy,
* wykonanie kopii bezpieczeństwa,
* usunięcie bardzo starych logów zgodnie z konfiguracją.

Przykładowo:

```cron
15 4 1 * * /opt/smog-ai/scripts/run_monthly.sh
```

# 4. Wymagania dotyczące cron

Obsłuż profesjonalnie typowe problemy związane z `cron`.

## 4.1. Pełne ścieżki

Nie zakładaj, że `cron` posiada taki sam `PATH` jak użytkownik interaktywny.

Każdy skrypt powinien używać pełnych ścieżek do:

* katalogu projektu,
* interpretera Python,
* środowiska `.venv`,
* plików konfiguracyjnych,
* bazy danych,
* logów.

Przykład:

```bash
/opt/smog-ai/.venv/bin/python -m smog_ai pipeline
```

## 4.2. Blokada przed równoległym uruchomieniem

Zadanie nie może uruchomić się drugi raz, jeśli poprzednie wykonanie nadal trwa.

Zastosuj `flock`, na przykład:

```bash
/usr/bin/flock -n /var/lock/smog-ai-hourly.lock \
    /opt/smog-ai/scripts/run_hourly_internal.sh
```

Jeśli nie uda się uzyskać blokady:

* proces ma zakończyć się kontrolowanie,
* zdarzenie ma być zapisane w logu,
* nie należy traktować tego jako krytycznej awarii.

## 4.3. Kody zakończenia

Każdy skrypt i każde polecenie CLI musi zwracać poprawny kod:

* `0` – sukces,
* kod niezerowy – błąd,
* osobny kod można zastosować dla częściowego sukcesu.

## 4.4. Logowanie

Każde zadanie cron ma zapisywać:

* czas rozpoczęcia,
* czas zakończenia,
* czas wykonania,
* identyfikator uruchomienia,
* wykonane etapy,
* liczbę pobranych rekordów,
* liczbę nowych rekordów,
* liczbę duplikatów,
* liczbę błędów,
* status publikacji.

Logi powinny trafiać:

* do katalogu `logs/`,
* opcjonalnie do `journald` przez `logger`,
* do osobnych plików dla zadań godzinowych, dziennych i treningowych.

Zastosuj rotację logów.

## 4.5. Zmienne środowiskowe

`cron` nie może polegać na interaktywnym profilu użytkownika.

Skrypty mają jawnie ładować konfigurację z pliku:

```text
/etc/smog-ai/smog-ai.env
```

lub:

```text
/opt/smog-ai/.env
```

Plik `.env` nie może znajdować się w repozytorium.

Przykładowe zmienne:

```env
SMOG_AI_ENV=production
SMOG_AI_CONFIG=/etc/smog-ai/config.yaml
SMOG_AI_DATABASE_URL=sqlite:////var/lib/smog-ai/smog.db

PUBLISH_API_URL=https://example.org/api/v1
PUBLISH_API_TOKEN=...

LOG_LEVEL=INFO
TZ=Europe/Warsaw
```

## 4.6. Obsługa przerwy w działaniu komputera

`cron` nie wykona zadań, gdy komputer jest wyłączony.

Dlatego po każdym uruchomieniu pipeline powinien:

* sprawdzić czas ostatniego udanego pobrania,
* wykryć brakujące przedziały czasu,
* spróbować uzupełnić możliwe dane historyczne,
* wyraźnie oznaczyć luki, których nie da się uzupełnić,
* nie zakładać, że poprzednie zadanie cron rzeczywiście się wykonało.

Pipeline powinien być odporny na przerwy trwające wiele godzin lub dni.

Opcjonalnie przygotuj konfigurację `anacron`, ale podstawowym mechanizmem ma pozostać `cron`.

# 5. Idempotentny pipeline

Każdy etap musi być możliwy do bezpiecznego ponownego uruchomienia.

Ponowne wykonanie:


* tworzyć duplikatów,
* usuwać poprawnych danych,
* nadpisywać historycznych prognoz,
* przypisywać rzeczywistych wyników do niewłaściwych prognoz,
* wielokrotnie publikować tych samych rekordów jako nowe.

Każdy pipeline powinien posiadać:

```text
run_id
started_at
finished_at
status
current_stage
records_downloaded
records_inserted
records_skipped
warnings_count
errors_count
```

Statusy:

```text
running
success
partial_success
failed
skipped_locked
```

```text

```

# Wymagania dotyczące Harmonogramu zadań Windows

## Pełne ścieżki

Nie zakładaj, że zadanie posiada taki sam `PATH` jak interaktywna sesja użytkownika.

Skrypty mają używać pełnych ścieżek do:

* katalogu projektu,
* interpretera Python,
* środowiska `.venv`,
* pliku konfiguracji,
* pliku `.env`,
* bazy danych,
* modeli,
* snapshotów,
* logów.

Przykład:

```powershell
$ProjectRoot = "C:\SmogAI"
$PythonExe = "C:\SmogAI\.venv\Scripts\python.exe"

& $PythonExe -m smog_ai pipeline
```

Nie polegaj na aktywowaniu środowiska poleceniem `Activate.ps1`. Wywołuj bezpośrednio interpreter:

```text
C:\SmogAI\.venv\Scripts\python.exe
```

## Katalog roboczy

Zadanie musi jawnie ustawiać katalog roboczy:

```powershell
Set-Location -LiteralPath "C:\SmogAI"
```

W konfiguracji zadania ustaw również:

```text
Start in: C:\SmogAI
```

Nie używaj względnych ścieżek zależnych od bieżącego katalogu.

## Blokada przed równoległym uruchomieniem

To samo zadanie nie może działać równolegle w wielu instancjach.

Na poziomie Harmonogramu zadań ustaw:

```text
If the task is already running:
Do not start a new instance
```

Dodatkowo zaimplementuj blokadę aplikacyjną.

Preferowane rozwiązania:

* nazwany systemowy mutex Windows,
* plik blokady zawierający PID, czas uruchomienia i identyfikator zadania,
* mechanizm w lokalnej bazie danych z kontrolą wygasłych blokad.

Blokada powinna zawierać:

```text
lock_name
process_id
host_name
started_at
heartbeat_at
expires_at
```

Jeżeli blokada istnieje, ale proces już nie działa lub blokada wygasła, system powinien bezpiecznie ją przejąć.

Nie opieraj blokady jedynie na sprawdzeniu istnienia zwykłego pliku bez weryfikacji procesu i czasu wygaśnięcia.

## Kody zakończenia

Każdy skrypt PowerShell oraz każde polecenie CLI musi zwracać poprawny kod zakończenia:

```text
0 — sukces
1 — błąd ogólny
2 — błąd konfiguracji
3 — błąd bazy danych
4 — częściowy sukces
5 — zadanie pominięte z powodu blokady
6 — błąd publikacji, przy zachowaniu danych lokalnych
```

Skrypty PowerShell mają propagować kod zwrócony przez Pythona:

```powershell
& $PythonExe -m smog_ai pipeline
$ExitCode = $LASTEXITCODE
exit $ExitCode
```

## Obsługa błędów PowerShell

Każdy skrypt powinien rozpoczynać się od:

```powershell
Set-StrictMode -Version Latest
$ErrorActionPreference = "Stop"
```

```powershell
try {
    # wykonanie
}
catch {
    # zapis błędu
    exit 1
}
finally {
    # zwolnienie zasobów i blokad
}
```

# Instrukcja instalacji na Windows

Dostarcz kompletną instrukcję PowerShell, przykładowo:

```powershell
Set-Location C:\SmogAI

py -3.12 -m venv .venv

Set-ExecutionPolicy -Scope Process -ExecutionPolicy Bypass

.\.venv\Scripts\python.exe -m pip install --upgrade pip
.\.venv\Scripts\python.exe -m pip install -r requirements.txt

Copy-Item .env.example C:\ProgramData\SmogAI\smog-ai.env
Copy-Item config.example.yaml C:\ProgramData\SmogAI\config.yaml

.\.venv\Scripts\alembic.exe upgrade head

.\.venv\Scripts\python.exe -m smog_ai collect-all
.\.venv\Scripts\python.exe -m smog_ai pipeline
.\.venv\Scripts\python.exe -m smog_ai healthcheck

.\scripts\Install-ScheduledTasks.ps1
```

Uwzględnij konieczność uruchomienia wybranych poleceń jako administrator wyłącznie tam, gdzie jest to rzeczywiście wymagane.

# Kryterium ukończenia wersji Windows

Po wykonaniu:

```powershell
py -3.12 -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
.\.venv\Scripts\alembic.exe upgrade head

.\.venv\Scripts\python.exe -m smog_ai collect-all
.\.venv\Scripts\python.exe -m smog_ai pipeline
.\.venv\Scripts\python.exe -m smog_ai report
.\.venv\Scripts\python.exe -m smog_ai healthcheck

.\.venv\Scripts\pytest.exe

.\scripts\Install-ScheduledTasks.ps1

Get-ScheduledTask -TaskPath "\SmogAI\"
Get-ScheduledTaskInfo -TaskName "Hourly Pipeline" -TaskPath "\SmogAI\"
```

system ma:

* utworzyć lokalną bazę,
* pobrać dane GIOŚ i IMGW,
* zapisać pomiary bez duplikatów,
* wykonać prognozy,
* zweryfikować wcześniejsze prognozy,
* przygotować snapshot,
* opublikować dane lub zachować je w outboxie,
* utworzyć cztery zadania Harmonogramu zadań,
* poprawnie blokować równoległe uruchomienia,
* uruchamiać się po pominiętym terminie,
* prowadzić logi,
* tworzyć kopie bezpieczeństwa,
* przechodzić testy.
